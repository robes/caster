# Project Structure

This document describes the layout of the repository, the conventions it
follows, and the workflows for common tasks. It is the canonical reference for
new collaborators and for future-us six months from now.

The repository is a **template** for machine-learning model development. It is
not specific to any dataset, task, or framework — it scaffolds the full
lifecycle: source data → preprocessing → splits → training → evaluation →
reporting → release.

Caster is built on a small set of mature tools, and the layout follows their
conventions wherever they have one:

- **Hydra** owns configuration and run directories.
- **DVC** owns data and artifact versioning, and (optionally) the pipeline DAG.
- **git** is the source of truth for code, and the anchor every run is pinned to.
- **Croissant** is the schema for dataset documentation.
- **GTO** versions releases; **RO-Crate + BagIt** package them for archival.

Where these tools dictate a structure, the template adopts it rather than
inventing its own. Where they are silent, the template supplies a convention.

## Goals

Three priorities of equal weight — none traded away for another:

- **Reproducibility.** Any result is traceable to a specific commit, config,
  data version, and environment.
- **Transparency.** A collaborator can open a run directory or a data-source
  record and understand what produced it without asking.
- **Simplicity.** Client-side tools, git as the source of truth, no mandatory
  servers. A DVC *local remote* (a directory) needs zero infrastructure; a cloud
  remote is one config line away.

## What each tool owns

The structure is easiest to understand by which tool is responsible for each
part of it. The three bold rows below are where the template adds something; the
rest is the underlying tools.

| Concern | Owned by | In the layout |
|---|---|---|
| Code state | git | the whole repo |
| Config composition + per-run config record | Hydra | `configs/`, `outputs/**/.hydra/` |
| Run directories | Hydra | `outputs/YYYY-MM-DD/HH-MM-SS/` |
| Data & artifact bytes + versioning | DVC | `data/`, `*.dvc`, `dvc.lock`, the remote |
| Pipeline DAG (optional) | DVC | `dvc.yaml` |
| Declared environment | `uv.lock` | committed at the root |
| **Commit ↔ run-dir + actual environment** | **Caster** | `outputs/**/_provenance.json` |
| **Dataset documentation** | **Croissant** (+ Caster convention) | `data_sources/` |
| Release versioning + retrieval | GTO + `dvc get` | git tags |
| **Archival bundle** | RO-Crate + BagIt (+ Caster glue) | `releases/` |

## Run directories and provenance

Run directories are where the most structure comes directly from a tool, because
Hydra owns them.

**Hydra owns the run directory.** Every invocation of a Hydra entry point gets
its own output directory, by default `outputs/YYYY-MM-DD/HH-MM-SS/`, and Hydra
writes a `.hydra/` subdirectory into it containing:

- `config.yaml` — the fully *composed* config for this run (all groups merged,
  all overrides applied). This is the authoritative record of what parameters
  the run used; nothing else needs to freeze the config.
- `overrides.yaml` — the command-line overrides, recorded separately.
- `hydra.yaml` — Hydra's own resolved configuration.

The directory name is purely for human organization — the commit is recorded
reliably in the run-stamp (below), so there is no need to encode it in the path.
Use Hydra's default scheme.

**Caster adds the run-stamp.** No tool in the stack records *which commit and
which actual environment* produced a given run directory. Caster closes that
gap with a Hydra callback that writes `_provenance.json` into every run
directory:

```json
{
  "git": { "commit": "39abc27…", "branch": "main", "dirty": false },
  "environment": {
    "python": "3.11.8",
    "platform": "…",
    "uv_lock_sha256": "a1b2c3…",
    "sync_mode": "frozen",
    "packages_observed": ["…"]
  },
  "completed": true,
  "created_at": "2026-05-29T18:04:11Z",
  "stats": { "val_accuracy": 0.91 }
}
```

The callback is registered once in `configs/hydra/default.yaml`:

```yaml
hydra:
  callbacks:
    run_stamp:
      _target_: caster.provenance.RunStampCallback
```

so every run is stamped automatically — sweeps included — with nothing to
remember at the command line. The stamp is written on job *end*, so a crashed
run leaves a directory with no `_provenance.json`: the file's **absence** is the
completion-failure signal, exactly the property the layout relies on.

Recorded timestamps are UTC, ISO-8601, `Z`-suffixed. Hydra's directory-name
timestamp is local time, since it exists for the developer organizing
`outputs/`. The full design — including why the environment is recorded as a
lockfile hash + sync mode + observed-package tripwire rather than a bare package
dump — is in [`docs/PROVENANCE.md`](docs/PROVENANCE.md).

**Non-Hydra stages stamp themselves.** A pipeline stage that does not go through
Hydra (a plain script driven by a DVC stage) writes its stamp by appending one
command:

```yaml
# dvc.yaml
stages:
  preprocess_brain_mri:
    cmd:
      - python scripts/preprocess.py +data=brain_mri
      - caster provenance stamp data/processed/brain_mri --stats n_samples=1234
    deps: [scripts/preprocess.py, data/raw/brain_mri]
    outs: [data/processed/brain_mri]
```

DVC runs the commands in order and aborts the stage if the first fails, so the
stamp is reached only on success — and `dvc.lock` is rewritten only on success
too. The completion semantics are enforced twice over.

## Directory reference

### `configs/` — Hydra owns this

Configuration follows Hydra's **config-group** model, not a flat set of
copy-and-edit files. The base `configs/config.yaml` declares composition
defaults and the `hydra` block; subdirectories are config groups you compose
from:

- `configs/data/` — one config per dataset or data source.
- `configs/model/` — one per architecture.
- `configs/split/` — split-generation configs.
- `configs/eval/` — evaluation configs.
- `configs/experiment/` — full experiment configs that select one option from
  each group and layer overrides on top. A complete run is usually
  `python scripts/train.py +experiment=<name>`.
- `configs/hydra/` — Hydra's own settings, including `default.yaml` that
  registers the run-stamp and split-properties callbacks.
- `configs/release/` — one config per `(release_tag, model_id)` for
  `caster.package`.

**One source of truth: the Hydra config files; DVC watches them.** A parameter
lives in exactly one place — its Hydra config under `configs/`. The scripts read
those configs at runtime, and DVC's `params:` entries in `dvc.yaml` point at the
*same files* (DVC can track keys within any YAML), so the config you edit, the
config the script uses, and the config DVC watches for re-runs are identical.
There is no separate `params.yaml`. This avoids the trap of a parameter recorded
in two files kept in sync by hand: change `configs/split/standard.yaml` and both
the next run *and* DVC's change-detection see the new value, with no drift
possible. Provenance follows the same single source — Hydra writes the composed
`.hydra/config.yaml` (CLI overrides captured in `.hydra/overrides.yaml`) into the
run dir, and DVC pins the watched config keys in `dvc.lock`.

### `data_sources/` — Croissant, one record per dataset

External datasets are documented here, one record per dataset, committed to git.
Listing this directory answers "what external data does this project use, and
how would someone else get it?"

The records are **Croissant** (the MLCommons standard), not an invented schema.
Three situations, covered fully in [`docs/DATA_SOURCES.md`](docs/DATA_SOURCES.md):

1. **Already has Croissant** (Hugging Face / Kaggle / OpenML) — download the
   JSON-LD file into `data_sources/`; no Caster tool needed.
2. **DOI / archival source, no Croissant** — author a short `<name>.yaml` and run
   `caster data emit <name>` to produce valid Croissant JSON-LD.
3. **Assembled privately** — author locally (the MLCommons Croissant editor can
   derive a starting point), document how it was built in `provenance:` prose.

**Scope.** Library-managed datasets that pin their own version (a Hugging Face
`datasets` load with a revision, a TorchVision dataset) need no record — their
identity travels in the Hydra config that consumes them.

**Validation and coverage.** `caster data validate` checks every
record is well-formed Croissant (via the `mlcroissant` library) and that every
DVC-tracked dataset under `data/` has a matching record. Wire it into
pre-commit so a tracked dataset can never be undocumented.

**Pinning is DVC's job, not a manifest tool's.** The dataset's *bytes* are
pinned by `dvc add` (the `.dvc` pointer and `dvc.lock` carry per-file hashes);
the Croissant record describes *what the data is*; the `fetch:`/`provenance:`
prose says how to obtain or rebuild it. The three are complementary.

### `src/` — all importable packages

The repository uses a **src layout**: every importable package lives under
`src/`, discovered by setuptools (`where = ["src"]`). Two packages sit side by
side there — the shared infrastructure and your project code — so the boundary
between them is a clear directory split rather than a difference in location.

#### `src/caster/` — the thin shared layer

Installed as the `caster` package. You should not need to edit it. It is small
by design: its code is justified only where it encodes knowledge no library has.

- `caster.provenance` — the run-stamp. `RunStampCallback` for Hydra runs;
  `caster provenance stamp <dir> [--stats k=v]` for non-Hydra stages.
- `caster.data` — `caster data validate` and `… emit <name>`. Delegates
  Croissant generation and validation to `mlcroissant`.
- `caster.package` — `caster package <release_config.yaml>`. Connective
  code over the `rocrate` and `bagit` libraries; pins the source to the run's
  commit and arranges the provenance chain.

The CLI modules resolve the project root by locating the git/DVC root, so they
work from anywhere inside the project.

#### `src/<project>/` — your code

Your project's own code, imported as `<project>.…` (e.g. `from <project>.models
import ...`). Packaging it under a project-named directory keeps it namespaced —
avoiding collisions with common top-level names like `models` or `datasets`
(the latter shadowing the Hugging Face library). Modules should be free of
import-time side effects and should not hardcode paths.

- `src/<project>/datasets/` — dataset classes, transforms, the logic that turns
  files on disk into model-ready arrays. (Not to be confused with the top-level
  `data/`, which holds the actual files.)
- `src/<project>/models/` — model definitions, one architecture per file when
  reasonable. The template is framework-agnostic: PyTorch, TensorFlow/Keras,
  JAX, scikit-learn, XGBoost all fit. Release packaging never imports this code,
  so no particular base class is required.
- `src/<project>/training/` — training loops, evaluation loops, losses, metrics.

#### Model packaging convention

Release packaging treats the trained checkpoint as **opaque bytes** —
`caster.package` never imports your model class, loads weights, or inspects
architecture. This is what keeps packaging framework-agnostic: a PyTorch
`safetensors`, a scikit-learn `skops`, and an XGBoost `.ubj` file all flow
through the same path.

The consequence is that **architecture must travel separately from weights**.
Save checkpoints in a portable, framework-appropriate format rather than a
Python-pickle one:

| Framework | Format | API |
|---|---|---|
| PyTorch / TF-Keras / JAX-Flax | `safetensors` | `safetensors.torch.save_file`, … — weights only |
| scikit-learn | `skops` | `skops.io.dump` / `skops.io.load` |
| XGBoost | native `.ubj` | `Booster.save_model("model.ubj")` |

These are established libraries with stable APIs; the template does not wrap
them. For a runnable loader, ship inference code in the release (or document the
loader), since `safetensors` stores weights only.

### `scripts/` — your pipeline entry points

One thin entry point per lifecycle step; the real logic lives in `src/`.

- `fetch.py` — acquires the raw data (the pipeline input). In the example it
  generates synthetic data; a real fetch downloads/materializes per the dataset's
  Croissant `fetch:` instructions. A Hydra app, so even acquisition is stamped.
- `preprocess.py` — transforms raw → processed. A Hydra app.
- `split.py` — produces the train/val/test split; a Hydra app, so the
  split-properties callback fires.
- `train.py` — trains a model; writes the canonical checkpoint to a stable path
  (the train stage's DVC `outs`) and to its Hydra run dir (provenance).
- `evaluate.py` — ONE script, two roles by config and pipeline membership:
  `+eval=validation` (val split) is a DVC stage run every `dvc repro` for model
  selection; `+eval=holdout` (test split) is the held-out final test, kept OUT of
  the pipeline and run once at publication. The scoring code is identical; the
  split and the in-/out-of-DAG placement are the only differences.

Every stage is a Hydra app, so every stage self-stamps via the registered
callbacks — one uniform model across the whole pipeline.

A training or eval script is a Hydra app (`@hydra.main(...)`); the run-stamp
callback fires for it with no extra code. A preprocessing or split script that
runs outside Hydra appends the stamp command in its `dvc.yaml` stage.

### `data/` — DVC owns the bytes, organized by pipeline stage

Gitignored bytes; committed pointers. The top-level layout is **stage-aligned**,
mirroring the DAG: `raw/` holds pipeline inputs, `processed/` (and optionally
`features/`) holds stage outputs. When a project has more than one dataset, each
gets its own directory *inside* the stage level — stage-over-dataset, so the
input/output boundary stays the top-level split.

```
data/
├── raw/                          # pipeline INPUTS (DVC dependencies)
│   ├── brain_mri/                # one source dataset, in its native structure
│   ├── brain_mri.dvc             # committed DVC pointer (hashes the directory)
│   ├── clinic_cohort/            # a second source dataset
│   └── clinic_cohort.dvc
├── processed/                    # preprocessing stage OUTPUTS (pinned by dvc.lock)
│   ├── brain_mri/                # produced by the preprocess stage for brain_mri
│   └── clinic_cohort/
└── features/                     # OPTIONAL further stage outputs
```

The conventions:

- **Stage at the top, dataset within.** `raw/` vs `processed/` is the stage
  distinction (input vs output); `<dataset_name>/` is a grouping inside each. A
  single-dataset project can collapse to `data/raw/` directly; the nested form
  is the general case and costs nothing.
- **A directory tracks as one artifact.** `dvc add data/raw/brain_mri` produces a
  single `brain_mri.dvc` pointer for the whole directory, however many files it
  contains — so per-dataset granularity (one pointer, one `dvc pull`, one hash)
  is preserved without per-file pointers. A BDBag or tarball landing at
  `data/raw/brain_mri/` keeps its native structure.
- **Raw is `dvc add`ed; processed is a stage output.** Raw data has no producing
  stage, so you `dvc add` it explicitly (committed `.dvc` pointer, bytes in the
  cache + remote). Preprocessed data *is* produced by a stage, so it is pinned by
  that stage in `dvc.lock` as an `out` — not added separately. Their pinning
  differs because their stage roles differ.
- **The parent-child link is a DAG edge, not a naming rule.** A preprocessed
  dataset's relationship to its source is expressed by the preprocess stage's
  `deps`/`outs` in `dvc.yaml` (`deps: data/raw/brain_mri`, `outs:
  data/processed/brain_mri`), which `dvc repro` understands and re-runs on
  change — rather than inferred from a sibling name.
- **Huge source files may be left untracked deliberately.** Reference them in
  config and document them in `data_sources/` without `dvc add`; for an integrity
  check without re-hosting the bytes, keep a plain `sha256sum` manifest alongside.
  DVC won't treat them as pipeline deps in that case.
- **Verifying and restoring.** `dvc status` is the verifier; `dvc checkout` /
  `dvc pull` restores the exact tracked version.

Set `cache.type = reflink` (or `hardlink`/`symlink`) when the DVC remote is on
the same filesystem, so a local remote does not duplicate bytes.

### `outputs/` — Hydra run directories

Gitignored by default. Each Hydra run creates `outputs/YYYY-MM-DD/HH-MM-SS/`
containing `.hydra/` (Hydra's composed config + overrides), `_provenance.json`
(the run-stamp), and whatever your training code writes (checkpoints, metrics,
predictions, tensorboard). A run directory without `_provenance.json` is an
incomplete or crashed run — debug evidence, not a result.

If you want a training run's outputs versioned and shareable (not just
reproducible from code + data + seed), make the run directory or its checkpoints
a DVC output of a `dvc.yaml` stage; then `dvc push` stores them and `dvc.lock`
pins them. Otherwise runs stay local and are reproduced by re-running.

Evaluation is its own step. The eval config points at a training run and a
checkpoint within it; the relationship lives in the config, not in a forced
directory nesting. The run directories are also TensorBoard-compatible: if your
training writes event files into its run dir (the example's scikit-learn model
has no training curve to log, so it doesn't), `tensorboard --logdir outputs/`
groups runs by their relative paths.

### `splits/` and split artifacts

A split is a generated artifact produced by a **Hydra app** (the example
`split.py`), so its run is auto-stamped and — because the run's config
has a `split:` block — the split-properties callback also fires:

- The split **config** under `configs/split/` is the committed source of truth.
  It declares where the artifact lands (`output_dir`/`filename`), the partition
  column, and optionally `class_column`/`group_column` so the callback can
  capture class balance / group disjointness.
- The split **artifact** (e.g. `splits.csv`) is written to the stable
  `split.output_dir` (a DVC stage output that training configs reference), *not*
  into the timestamped Hydra run dir. `dvc.lock` / the `.dvc` pointer pins it and
  `dvc pull` restores it.
- The split **properties** (`_split_properties.json`) land in the Hydra run dir
  alongside `_provenance.json` — Caster's record *about* the split (sizes,
  fractions, index hashes, declared task tiers), distinct from the split data
  itself. The packager collects it into releases.

**Determinism is still expected, but verification is tolerant.** Seed every
random operation so a regenerated split is *equivalent*. But a regenerated split
need not be byte-identical — a different RNG can assign different rows while
preserving sizes and balance — so equivalence is checked against
`_split_properties.json` (structural tier always; class balance / group
disjointness when declared), not by demanding identical bytes. A training config
references a split by its path; pinning it (via DVC) plus the properties record
pins which samples a run used and how to verify an equivalent regeneration.

### `releases/` — archival bundles

Gitignored. `caster.package` produces one archival bundle per
`(release_tag, model_id)`: an **RO-Crate** (the description layer, written by the
`rocrate` library) wrapped in a **BagIt** bag (the verifiable-transfer layer,
written by `bagit`). The payload carries the checkpoint as opaque bytes, the full
provenance chain (the run's `.hydra/` config, its `_provenance.json`, the DVC
pointer files, the `data_sources/` records, the eval artifact), and a
`git archive` of the source pinned to the commit in the run's stamp.

```
<release_tag>_<model_id>.zip
└── <release_tag>_<model_id>/            # BagIt bag root
    ├── bagit.txt, bag-info.txt          # BagIt declaration + metadata (Source-Commit recorded)
    ├── manifest-sha256.txt              # checksums of every payload file
    ├── fetch.txt                        # present if any dataset has disposition: fetch
    └── data/                            # BagIt payload == RO-Crate root
        ├── ro-crate-metadata.json       # the description layer
        ├── model/                       # checkpoint bytes + .sha256 sidecar
        ├── provenance/
        │   ├── config/                  # the run's .hydra config + overrides
        │   ├── run/                     # _provenance.json + _split_properties.json
        │   ├── data_sources/            # Croissant records for each dataset
        │   └── eval/                    # metrics + predictions
        ├── data_manifest.sha256         # portable hashes of referenced data (no DVC remote dep)
        ├── splits/                      # split CSVs (bytes by default)
        ├── source/<project>-<tag>.tar.gz   # git archive at the run commit
        └── datasets/<name>/             # only for datasets with disposition: embed
```

**What travels is determined by regenerability**, because the bundle is for a
reader who has only the bundle (not your DVC remote). Raw data → Croissant
*descriptor* only; processed data → descriptor by default, bytes opt-in; splits →
bytes by default (they're small and pin which samples were used); checkpoint →
bytes. Raw `.dvc`/`dvc.lock` pointers do **not** travel — they address a remote
the reader can't reach. Instead, `data_manifest.sha256` carries the data *hashes*
(identity) extracted from the project's integrity record, so re-obtained data can
be verified without the remote.

**Per-dataset disposition** overrides the defaults (the Croissant record and the
`data_manifest.sha256` entry always travel):

- **omit** (default for raw) — descriptor + hash only; the reader re-obtains the
  bytes via the record's `fetch:` instructions and verifies against the manifest.
- **fetch** — referenced via BagIt `fetch.txt` / RO-Crate `contentUrl`;
  materialized on demand with `bdbag --resolve-fetch`.
- **embed** — bytes pulled at the run commit (`dvc get … --rev <commit>`) into the
  payload, for a fully self-sufficient archival deposit.

Verification is **tolerant**: a regenerated split or processed dataset is checked
for *equivalence* (matching sizes, fractions, class balance — from
`_split_properties.json`), not bit-identity, and metrics within ~1–2 decimal
places. A stored hash is a strong signal, not a pass/fail gate.

Versioning and retrieval are separate and delegated to **GTO** + DVC:
`gto register <model> --version v1.0.0 [<ref>]` tags a release; `dvc get <repo> <path> --rev
<tag>` pulls it. Caster does not reimplement that. Full detail in
[`docs/PACKAGING.md`](docs/PACKAGING.md).

### `reports/` and `notebooks/`

`reports/` holds PDFs, figures, and artifacts for human readers, generated from
runs; filenames should include a date. `notebooks/` is exploratory only —
anything you will cite, defend, or publish moves into `src/` and runs via a
script. Notebooks are for thinking, not for the record.

### `experiments.md` (optional)

A flat, human-readable log of runs, regenerable from the `_provenance.json`
stamps (each run contributes a row: commit, key stats, timestamp). It is
optional: `dvc exp show` covers run comparison for DVC-driven experiments, and
the stamps are the durable record either way. If you keep it, treat the machine
columns as regenerable and the Notes column as human-authored.

## Workflows

This document is the layout-and-conventions reference. For the operational
commands — first-time setup, running the pipeline, the held-out test, packaging a
release — see the README's [Getting started](README.md#getting-started)
walkthrough and its [Common tasks](README.md#common-tasks) quick-reference. Each
duty's detailed how-to lives in its doc:
[`DATA_SOURCES.md`](docs/DATA_SOURCES.md) (documenting and tracking data),
[`PROVENANCE.md`](docs/PROVENANCE.md) (stamps, the ledger), and
[`PACKAGING.md`](docs/PACKAGING.md) (releases). The conventions those commands
follow are below.

## Conventions

### Reproducibility

- **The run-stamp is automatic for Hydra runs and one line for DVC stages.** Do
  not hand-write provenance metadata; the callback and the `caster.provenance
  stamp` command own it.
- **Parameters live once, in the Hydra config files.** The scripts read them;
  DVC's `params:` entries watch the same files for re-runs. No separate
  `params.yaml`, so a value can't drift between "what the script used" and "what
  DVC watched." Both the composed `.hydra/config.yaml` (in the run dir) and the
  watched config keys (in `dvc.lock`) record what ran.
- **Seed everything.** The seed lives in the config; set framework determinism
  flags if bit-exactness matters (though common seeds, not pinned GPUs, are the
  assumed level — expect metrics within ~1–2 decimal places).
- **Document data provenance.** Every external dataset has a `data_sources/`
  record. No hand-wave "download from this website" in code comments.
- **Never edit artifact directories or DVC outputs by hand.** If a run is bad,
  leave it and create a new one. Append, don't mutate.
- **A missing `_provenance.json` means the run did not complete.** Treat such
  directories as debug evidence, not results.

### Data and splits

- Pin dataset and split *bytes* with DVC (`dvc add` / `dvc.yaml` outputs);
  commit the pointers, not the bytes.
- Split generation must be deterministic (seeded), so a config and its stored
  artifact never drift.
- Every DVC-tracked dataset must have a `data_sources/` record
  (`caster.data validate` enforces it).

### Code

- Scripts in `scripts/` are entry points only; logic goes in `src/`.
- Use `ruff` (lint + format) via pre-commit so style never enters discussion.
- Feature branches and PRs even for small teams — see
  [`CONTRIBUTING.md`](CONTRIBUTING.md).

### Naming

- Run directories: Hydra's default `outputs/YYYY-MM-DD/HH-MM-SS/` (override
  `hydra.run.dir` if you want a tag or commit in the name).
- Config files: snake_case and descriptive (`baseline.yaml`, not `config2.yaml`).
- Data-source records: `<dataset_name>.{yaml,json}`, matching the directory under
  `data/`.

## The unopinionated boundary

The template sets defaults but does not lock them in:

- **DVC remote** defaults to a local directory; swap in S3/GCS/Azure/SSH by
  changing one remote URL.
- **Experiment tracking** defaults to none. The run directories are
  TensorBoard-compatible, so adding a writer that logs into the run dir gives you
  `tensorboard --logdir outputs/` alongside the run-stamp — enough at small
  scale (the template doesn't install or wire TensorBoard; bring your own
  logger). Add a Hydra logger config for W&B/MLflow/Neptune; the run-stamp keeps
  working alongside it.
- **Pipeline DAG** is optional. Run scripts by hand in order, or wire them into
  `dvc.yaml` stages for `dvc repro`. The run-stamp fires either way.
- **Framework** is yours. Caster never imports your model; the checkpoint is
  opaque bytes everywhere Caster touches it.
