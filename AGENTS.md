# Working in this repository (for coding agents)

This is a template for reproducible ML projects: a thin layer over git, Hydra,
DVC, Croissant, GTO, and RO-Crate/BagIt. This file is the orientation for an
automated agent. It is intentionally short; it points at the docs rather than
restating them.

## Orientation — where things are

- **What to do, end to end:** [`docs/HOWTO.md`](docs/HOWTO.md) — data → experiments → release.
- **Why it's built this way:** [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).
- **Layout and conventions:** [`PROJECT_STRUCTURE.md`](PROJECT_STRUCTURE.md).
- **Per-duty depth:** [`docs/DATA_SOURCES.md`](docs/DATA_SOURCES.md),

## Canonical commands

`make setup | test | lint | pipeline | check`, or directly: `uv run pytest`,
`uv run ruff check src scripts`, `uv run dvc repro`. After any change, run
`make check` (tests + lint) to confirm health. The project's own tools run via the
unified `caster` command (`caster <group> <command>`); the full list is in
[`docs/COMMANDS.md`](docs/COMMANDS.md).

## Machine-readable affordances — use these

The Caster commands are built to be driven by an agent. Prefer these over parsing
human text:

- **Capturing a run's directory.** Every Hydra run (any `scripts/*.py`) prints a
  final line `CASTER_RUN_DIR=<path>` on stdout. Capture it to know exactly which
  run you just produced — do **not** guess "the latest" by globbing `outputs/`
  timestamps, which is ambiguous under fast or concurrent runs. The same path is
  recorded inside that run's `_provenance.json` (`run_dir` field).
- **`--json` for querying/verifying.** `caster data validate`,
  `caster provenance ledger`, and `caster package` accept `--json`. In that mode
  stdout is *only* a JSON object — `{"ok", "command", "result", "problems"}` —
  with all human/warning text on stderr, so you can pipe stdout straight to a
  parser. `ok` mirrors the exit code. Use `ledger --json` to select a run by
  metric; `validate --json` to act on each problem; `package --json` to read the
  bundle's asset/warnings.
- **`package --dry-run`.** Reports what would be packaged and which warnings would
  fire (missing stamp/config/eval, HEAD fallback) and writes nothing. Use it to
  check a release config before building, then run without `--dry-run`.
  `package --card` prints the model card the bundle would carry, so its prose can
  be reviewed (and empty sections found) before a release.

Exit codes are reliable: 0 on success, non-zero on real failure. A non-zero exit
or `"ok": false` means stop and read the problems.

## Invariants — do not violate

These encode the design. Changing them silently breaks reproducibility:

- **The held-out test is run once, at publication, and is deliberately NOT in the
  DVC pipeline.** Never add `evaluate.py +eval=holdout` to `dvc.yaml`, and never
  use the held-out split for model selection — that is test-set leakage.
- **A parameter has exactly one home:** its Hydra config under `configs/`.
  `dvc.yaml` `params:` point at those files. Do not duplicate a value.
- **Never commit generated lockfiles' contents as fixtures or ship them:**
  `dvc.lock` and `uv.lock` are generated by the user's first `dvc repro` / `uv
  sync`. (`uv.lock` *is* committed by the user; it is just not shipped in the
  template.)
- **The `[tool.uv] override-dependencies` pin on `typer` is deliberate** — it
  works around a known upstream gto CLI break. Do not "clean it up."
- **`gto register` needs a `v`-prefixed three-part SemVer:** `--version v1.0.0`.
- **Provenance is automatic via Hydra callbacks**, not via code in the scripts.
  A run dir without `_provenance.json` means that run did not finish.

When a change would touch any of the above, prefer to ask rather than assume.
